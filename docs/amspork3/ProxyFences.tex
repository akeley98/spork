\sporkSection{Appendix: Proxy Fences}{sec:ProxyFences}

CUDA memory operations may be in the \emph{generic proxy} or \emph{async proxy} \cite{ptx}.
(There are others, but none are modelled by \sporkName{}).
Synchronizing operations in different proxies requires a \emph{cross-proxy fence}.
So far as we can tell,
all async proxy operations are ``followed by an implicit \emph{generic-async} proxy fence'' \cite{ptx}.
Therefore, the \sporkName{} compiler only has to generate cross-proxy fences
for cases where the compiled synchronization statement has the possibility of
causing a trace graph path (Section~\ref{sec:TraceConcatChk})
to exist from a generic proxy access's $\sporkTrPostAccess$
to a later async proxy access's $\sporkTrPreAccess$.

Recall that trace edges (Section~\ref{sec:TraceEdges}) are labelled with
a set of observers and a set of pending awaits, at least one not empty.
Suppose \emph{for now} that all $\sporkqtl$ can be categorized as
either generic proxy or async proxy (Section~\ref{sec:Qtl}).
A barrier variable name $\sporkx$ is categorized by analyzing all
$\texttt{Arrive}(\sporkQtlArrive)$ statements referencing $\sporkx$;
the variable name is generic proxy if \emph{any} such $\sporkQtlArrive$
contains a generic proxy $\sporkqtl$; otherwise, $\sporkx$ is async proxy.

We call an edge \emph{generic} if it is labelled with an observer containing a generic proxy $\sporkqtl$,
or if it is labelled with a pending await containing a generic proxy $\sporkx$.
The definition of \emph{async edge} is similar.
An edge may be both generic and async;
however, critically, it's not possible for an edge to be neither
(it must be labelled with at least one observer or at least one pending await,
and, for now, all $\sporkqtl$ or barrier variable names are categorized as generic or async).

The sequence of events we care about is a memory access in the generic proxy,
followed (in total trace order) by a memory access in the async proxy.
The first generates a $\sporkTrPostAccess$ event with no outbound async edges:
no observers with async proxy $\sporkqtl$ are possible,
and no pending awaits are possible as only TMA uses this feature.
The second generates a $\sporkTrPreAccess$ event with no inbound generic edges:
no observers with generic proxy $\sporkqtl$ are possible,
and no pending awaits are possible except for those special
$\sporkTrPreAccess$ added by the SMEM allocator
(Section~\ref{sec:SmemAppendix}; that we don't analyze this is potentially a gap in our analysis).

If a path exists between the two vertices,
at least one vertex on the path must have inbound generic edges and outbound async edges.
We guarantee that such vertices correspond to executing \sporkName{} synchronization statements
that were compiled to include a cross-proxy fence.
The \sporkName{} compiler upholds this guarantee by inserting a
cross-proxy fence in codegen when compiling certain \texttt{Fence} or
\texttt{Await} statements, according to the following case analysis
of possible trace events generated from executing the statement:

\sporkMainKey{Case \texttt{Fence($\sporkQtlArrive$, $\sporkQtlAwait$)}:}
A cross-proxy fence is only inserted if $\sporkQtlArrive$ contains generic proxy $\sporkqtl$
and $\sporkQtlAwait$ contains async proxy $\sporkqtl$;
otherwise, either inbound generic edges are impossible, or outbound async edges are impossible.

\sporkMainKey{Case \texttt{Arrive($\sporkQtlArrive$)}, referencing generic proxy $\sporkx$:}
No cross-proxy fence is inserted; the outbound edges (labelled only with pending awaits
referencing the generic proxy $\sporkx$) are generic.

\sporkMainKey{Case \texttt{Arrive($\sporkQtlArrive$)}, referencing async proxy $\sporkx$:}
No cross-proxy fence is inserted; the inbound edges (labelled only with observers
containing async proxy $\sporkqtl$) are async, by definition of ``$\sporkx$ is async proxy''.

\sporkMainKey{Case \texttt{Await($\sporkwScalarH$, $\sporkQtlAwait$, $\sporkz_\mathrm{lag}$)},
$\sporkwScalarH$ references generic proxy $\sporkx$:}
A cross-proxy fence is only inserted if $\sporkQtlAwait$ contains async proxy $\sporkqtl$;
otherwise, outbound async edges are impossible.

\sporkMainKey{Case \texttt{Await($\sporkwScalarH$, $\sporkQtlAwait$, $\sporkz_\mathrm{lag}$)},
$\sporkwScalarH$ references async proxy $\sporkx$:}
No cross-proxy fence is inserted, as only async inbound edges are possible.
(End cases)

Regarding the earlier ``suppose for now'':
this analysis would be undermined if the constructed trace graph contained edges
labelled by observers with $\sporkqtl$ categorized neither as generic proxy or async proxy.
This is the purpose of $\sporkQtlMask$:
for $\sporkTrPostAccess$ events corresponding to data RAM accesses (not registers, not mbarriers),
the mask contains only $\sporkqtl$ of data RAM class (either proxy).
For future work, we may look into more direct ways of modelling the proxy of a memory access,
and synchronization between different proxies.
In particular, the reasoning for split barriers (pending awaits) is somewhat convoluted,
and prevents us from modelling barriers that synchronize generic proxy accesses
with generic proxy accesses,
and synchronizes async proxy accesses with async proxy accesses,
but does not synchronize across proxies.
