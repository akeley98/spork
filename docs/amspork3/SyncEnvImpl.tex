\sporkSubsection{Sync Env Implementation}{sec:SyncEnvImpl}

We wrote an interpreter for the synchronization environment semantics using C++ and linked it to the Python-based Exo compiler.
The user calls \texttt{$\sporkp$.sync\_check($\cdot$)} with the concrete problem size passed as keyword arguments.
We check correctness by interpreting $\sporkp$'s body to completion or to an error state.
This is only possible without data values due to Exo's control-data separation:
the traced control flow and sequence of array indexing never depends on data values.

We greatly sped up the interpretation by de-duplicating visibility records in a hash table of type $\mathcal{P}(\sporkEnvVis)$.
For example, this allows us to memoize $\sporkenvVis \sporkAugmentVis \sporktr_d$ when tracing a new synchronization (Equation~\ref{eq:envConcatSync}).
We implement several optimizations that we have not fully reasoned to be sound,
mostly stemming from our hope to reduce the number of unique visibility records in the hash table:
\begin{itemize}
  \item For visibility records containing observers $\sporkob=(\sporktid, \sporkqtl)$ where $\sporkqtl$ is for that of an async instruction,
    the initially traced access sometimes expands the observer set on the $\sporktid$ axis to encompass an entire warp, warpgroup, or CTA,
    when this change would not affect $\sporksyncsWith$ for any subsequent synchronization
    due to this synchronization also being warp-, warpgroup-, or CTA-scoped.
    % This is Out-of-order Non-convergent Abstract Machine Optimization
  \item At the end of device tasks (Section~\ref{sec:KernelStructure}) or device function launches,
    we do the same $\sporktid$ expansion to encompass an entire cluster or entire device,
    respectively.
    % This is JoinThreads, intentionally ignored.
  % TODO item about eager free-on-arrive?
\end{itemize}
