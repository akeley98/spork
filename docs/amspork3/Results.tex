\sporkSection{Results}{sec:Results}

We implemented GEMM kernels for the \texttt{sm\_80} and \texttt{sm\_90a} architectures,
as well as a port of ThunderKitten's \texttt{sm\_90a} causal and non-causal forward flash attention kernels \cite{thunderkittens:mha_h100} \cite{shah2024flashattention3fastaccurateattention}.
For GEMM, we compared against the \texttt{cublasSgemm} and \texttt{cublasSgemmStridedBatched} functions \cite{cublas},
and for attention, we compared against the ThunderKittens original.
We used an \texttt{NVIDIA RTX A5000 Laptop GPU} (\texttt{sm\_80})
and \texttt{NVIDIA H100 PCIe} GPU (\texttt{sm\_90a}) for testing;
the latter has a theoretical peak of \texttt{756} TFLOPS for dense 16-bit MMA \cite{nvidia:h100-datasheet}.
We used nvcc \texttt{cuda\_12.3.r12.3/compiler.33492891\_0} to compile the CUDA C++ sources generated by Exo-GPU.

We tested each problem size over 105 iterations: 5 warm-up iterations, and 100 timed iterations,
with the pcg3d hash algorithm \cite{pcg3d} used to generate ``random'' input matrices.
Each iteration tested, in a randomized order, the reference kernel and all applicable
\sporkName{} kernel variants for that problem size.
We collected 100 time samples per tested (kernel, problem size)
and report the mean of the inter-quartile range (middle 50 samples).
For each plot, we report the best-performing \sporkName{} kernel for each problem size as \textsf{``Exo-GPU (specialized)''}
and the single best-performing \sporkName{} kernel as \textsf{``Exo-GPU (one kernel)''}.

\sporkMainKey{\texttt{sm\_90a} Cooperative GEMM:}
These kernels were our most successful.
They were scheduled starting from a simple baseline gemm kernel,
with rewrites used to introduce warp specialization, nested parallelism,
cluster \& TMA multicast support, and \texttt{wgmma} instructions;
all were safe rewrites except for a bounds-check exemption for TMA
(Section~\ref{sec:TmaLimitations}, Figure~\ref{fig:TmaUnsafeRewrite}).
We tested a variety of problem sizes for both \texttt{bf16} and \texttt{tf32} input precision,
swept over different tile and cluster sizes,
and tested non-split-k and split-k variants of the GEMM kernel,
with the split-k kernels using \texttt{cp.reduce.async.bulk} (TMA atomic \texttt{+=})
and split factors of 1, 2, 4, 8, and 16 (Figure~\ref{fig:Sm90aCoopPlots}).

\sporkMainKey{\texttt{sm\_80} GEMM:}
These kernels accelerate GEMM with 16-byte \texttt{cp.async} and warp-tile \texttt{mma} instructions.
Unlike the \texttt{sm\_90a} GEMM kernel,
we directly wrote the fully-optimized kernel, without scheduling rewrites.
This loses automated protection against dataflow logic bugs,
but still retains \sporkName{}'s instruction usage and synchronization checking.

The \sporkName{} kernel had notably lower performance than CUBLAS  (Figure~\ref{fig:Sm80Plots}).
Although we were successful in our core goals of imperative program representation,
explicit synchronization,
and explicit accelerator instruction usage,
our program representation was not low-level enough to allow optimizing
pointer arithmetic, index calculations, and other micro-inefficiencies in kernel design.

In lieu of pointers, \sporkName{} provides monolithic windows
(Section~\ref{sec:Grammar}, Figure~\ref{fig:WindowGrammar}),
which are lowered into complicated array indexing expressions.
This is to our disadvantage on \texttt{sm\_80};
the architecture does not support bulk copy (TMA)
and the \texttt{mma} instructions require register operands,
rather than reading SMEM directly as \texttt{wgmma} does,
leading to a large number of executed instructions
corresponding to pointer and index arithmetic (Figure~\ref{fig:Sm80ncu}).

We also had difficulty forcing uniform register usage (for storing warp-convergent values),
which to our knowledge is not directly expressible in C++ or PTX.
We are forced to rely on undocumented PTX-to-SASS compiler optimizations.
This is a devastating loss in the common case where non-uniform registers are the bottleneck,
and we are frustrated by the lack of clarity on how to use this feature,
especially given that collective analysis (Section~\ref{sec:CollAnalysis})
can trivially be extended to explicitly annotate which values are or are not warp-convergent
and therefore are amenable to the optimization.

From our read of CUTLASS \cite{cutlass},
it appears that certain \texttt{\_\_shfl\_sync} broadcast patterns can be used to trigger
uniform register usage.
We did not retrofit this to Exo for mapping index variables to uniform registers,
because Exo had no provision for custom instructions that produce $\sporkcontrol$-type values,
rather than data type.

\sporkMainKey{\texttt{sm\_90a} Attention:}
The story is similar here as it was for the \texttt{sm\_80} GEMM.
We were able to closely re-implement the reference ThunderKittens C++ kernel's
overall dataflow and usage of TMA and \texttt{wgmma}
by directly writing an \sporkName{} kernel that used those instructions.
Nevertheless, there is a non-trivial performance loss compared to the C++ original (Figure~\ref{fig:FaPlots}),
which we attribute to the combined effect of similar micro-inefficiencies as in the \texttt{sm\_80} GEMM kernel.
An additional suboptimality is that our hard-wired persistent kernel loop
(compiled from \texttt{cuda\_tasks} loops, Section~\ref{sec:KernelStructure})
is a poor fit for the causal kernel variant, leading to workload imbalance.
